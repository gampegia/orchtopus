# Evidence register: Claude Code setup, models and harness

Every number or choice about the Claude Code setup, the model and effort per role, or the harness design rests on an entry here. An entry names its source, the evidence level and the date it was last checked. Specs, plans, `CLAUDE.md` and agent files cite the entry id (for example `[EV-M1]`) instead of repeating the reasoning.

Rules (user decision, 2026-11-28):

- A value needs a current source: the official Claude Code or Claude Platform documentation, an Anthropic post (anthropic.com, claude.com, claude.dev), a dated statement by Anthropic Claude Code staff, or our own documented measurement. For tools that are not Anthropic's (WSL, VS Code, git), their own official documentation counts.
- Without such a source, follow the documented default or guidance, or make the value a setting whose default is the documented one. A value we choose ourselves is allowed only as a setting or a marked team rule, labelled **O**, with the reason written down.
- Sources must be current for the models in use. Older sources are marked "possibly outdated" until a newer one confirms them.
- Quality comes first. Usage optimisation is a later step; cache and context hygiene that the docs recommend apply now.
- Recheck every entry when a new model or a new major Claude Code version arrives, and at the start of each milestone that builds on it.

Evidence levels: **D** official documentation; **P** Anthropic post; **S** dated statement by Anthropic staff; **M-A** measured by Anthropic (internal, method not fully published); **M-O** our own measurement (spike or test, linked); **V** vendor statement without method; **O** own default or team rule (setting or marked rule, reason written).

Models in use: Fable 5.2, Opus 5.5, Sonnet 5.5, Haiku 5.5. Claude Code 2.1.332. Checked by an adversarial review against the sources on 2026-11-28.

## Isolation and coordination

| Id | Decision | Source | Level | Checked |
|---|---|---|---|---|
| EV-I1 | **WSL2 sandbox per project: a setting with a setup assistant; native Windows stays the default until Orchtopus can move a project into WSL itself.** The Claude Code sandbox does not exist on native Windows and works on WSL2; it limits writes and network for shell commands only; file tools, hooks and MCP servers run outside it; the Bash sandbox alone is not enough for fully unattended runs, for which the docs point to containers, VMs or the sandbox runtime. The repository belongs on the Linux file system; Explorer and VS Code reach it through `\\wsl.localhost` and the WSL extension (Microsoft and VS Code documentation). | code.claude.com/docs/en/sandboxing; code.claude.com/docs/en/sandbox-environments; learn.microsoft.com/windows/wsl/filesystems and /networking; code.visualstudio.com/docs/remote/wsl | D | 2026-11-28 |
| EV-I2 | **Task board: an Orchtopus-owned board in the SQLite event log, not Claude Code agent teams.** Agent teams are experimental, off by default, bound to the lead's lifetime, cannot resume in-process teammates, and fix teammates' permission mode at spawn; Orchtopus sessions are independent background sessions in their own worktrees. The design follows Anthropic's 1,000-agent post (shared task tree with claiming and splitting, notes, a landed log, one branch per agent, a separate step that lands work) and the agent-teams advice (one owner per file, 5 to 6 tasks per worker). Briefs carry objective, output format and boundaries (2025 research post, possibly outdated, not contradicted by newer sources). | agent-teams page; claude.dev/blog/safely-scaling-multi-agent-teams-with-fable-5-2 (Anthropic authors, 2026-11-09); anthropic.com/engineering/multi-agent-research-system (2025) | D, P | 2026-11-28 |
| EV-I3 | **User mods load in Orchtopus sessions, and a mod that decides on tool calls defeats our hooks and deny rules. Recommended for M2: switch such mods off per session with `enabledPlugins: false` in our `--settings` file (user approves in the M2 spec).** Mods are on by default from Claude Code 2.1.287 (terminal) and 2.1.286 (Desktop) (D). Observed on 2.1.332 without the built-in guard `cc-plugin-sec-default` (it loads only with managed settings or a Team or Enterprise login): a mod's `tool.call` that answers `{ result }` skips every settings `PreToolUse` and `PostToolUse` hook; a `tool.check` `allow` overrides a `PreToolUse` deny and a deny rule; a mod's `$.process.run` runs commands no hook sees. A classic plugin `PreToolUse` `allow` does not beat our deny. `--safe-mode` and `disableAllHooks` also stop our own hooks; `--bare` ends with "Not logged in" on a subscription login; `enabledPlugins: { "<id>": false }` in `--settings` removes that plugin for the session only and keeps our hooks. Detection: `claude plugin list --json` plus `claude plugin validate <installPath>` (`hooks: tool.call{…}` lines); the `SessionStart` input lists no plugins. With the guard, deny rules and `PreToolUse` blocks hold against users' mods (D, not observed). | code.claude.com/docs/en/mods; code.claude.com/docs/en/plugins/mods/admin and /events; code.claude.com/docs/en/plugins/loading; `docs/spikes/2026-11-28-mods-vs-hooks.md` | D, M-O | 2026-11-28 |
| EV-I4 | **`crossSessionInbound` takes `accept`, `hold` or `refuse`, and has no fixed default.** When unset, Claude Code decides per message from the permission modes of sender and receiver: a prompting receiver delivers unless the sender bypasses; a bypassing receiver holds unless the sender bypasses too. Messages from a session's own children are delivered when no value applies. When `--settings` sets the key, the `/config` row is hidden. Orchtopus sets it explicitly. A message never approves a permission. Needs 2.1.224 (macOS, Linux, WSL 2) or 2.1.234 (native Windows); `--bare` sessions bind no socket. | code.claude.com/docs/en/cross-session-messaging | D | 2026-11-28 |
| EV-I5 | **`CLAUDE_CODE_MESSAGING_TOKEN` and `CLAUDE_CODE_MESSAGING_SOCKET` on native Windows.** Each session binds a named pipe whose path is in `CLAUDE_CODE_MESSAGING_SOCKET`. The per-session token is in `CLAUDE_CODE_MESSAGING_TOKEN`. Both are exported to hooks and Bash commands (the docs do not say "only"). On Windows the first line sent must be `{"type":"auth","token":"<token>"}`, or the connection is closed; on Windows the token is the only proof of an own child process. Needs 2.1.234 or later. | code.claude.com/docs/en/cross-session-messaging | D | 2026-11-28 |
